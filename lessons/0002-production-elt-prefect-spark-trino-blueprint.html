Lesson 0002: Production ELT Blueprint

Orchestration với Prefect, Ingestion API tối ưu, Metadata Quality Rule, DLQ và Multi-target Storage (Trino / MinIO)

Mục Tiêu Bài Học (Learning Objective)

Trang bị trọn vẹn tư duy thiết kế hệ thống và giải pháp kỹ thuật mức Senior Data Engineer để vận hành pipeline dữ liệu thực tế tại môi trường doanh nghiệp: xử lý API bất định, chống cạn kiệt connection pool, kiểm soát chất lượng qua Dead Letter Queue (DLQ), lưu trữ đa mục tiêu (MinIO raw backup + Trino sandbox/prod) và xử lý xung đột đồng thời giữa Fact & Dimension.

1. Kiến Trúc Tổng Thể (System Architecture)

[REST APIs (Muc 1..4)] │ (Rate-limited, Keep-Alive, HTTP 429 Backoff) ▼ [Prefect Ingestion Worker] ──► Ghi Raw JSON ──► [MinIO: raw-backup/ (Immutable Bronze)] │ ▼ (Kích hoạt sau khi có file) [Apache Spark Cluster (Compute)] ├── 1. Schema Parser & Recursive Flattening (Unstructured - Silver Staging) ├── 2. Metadata Data Quality Rule Engine │ ├── Valid Records ──► Ghi [Trino: dev_db/sandbox] (Dành cho Data Scientist/DE test) │ │ └──► Ghi [Trino: prod_db/cleaned] (Iceberg ACID MERGE INTO) │ └── Invalid Records ─► Ghi [Dead Letter Queue: MinIO/Trino dlq_table] └── 3. Late-Arriving Dimension Resolver & Window Deduplication

2. Giải Quyết 5 Vấn Đề Kỹ Thuật Trọng Tâm

Vấn đề 1: Bảo vệ Connection Pool & Ổn định API Ingestion

Cảnh báo Senior DE: Tuyệt đối không khởi tạo HTTP connection trong hàm map() hay UDF từng dòng của Spark. Sẽ gây socket leak và DDOS máy chủ API.

  • Mô hình Decoupled (Khuyến nghị số 1): Để Prefect Task (Python httpx / aiohttp) đóng vai trò I/O Ingestor, kéo data về và dump thẳng file .json.gz lên MinIO. Spark chỉ đọc từ MinIO để tính toán song song.
  • Mô hình Spark Direct Ingestion: Nếu bắt buộc Spark kéo trực tiếp qua partition, phải dùng rdd.mapPartitions() kết hợp với Singleton Connection Pool (ví dụ urllib3.PoolManager hoặc requests.Session với HTTPAdapter(pool_connections=..., pool_maxsize=...)) để tái sử dụng socket trên từng Executor.
  • Cơ chế Backoff: Sử dụng Exponential Backoff + Full Jitter khi nhận HTTP 429 và đọc header Retry-After.

Vấn đề 2: Metadata Quality Rule & Dead Letter Queue (DLQ)

Thay vì lọc 2 lần gây quét dữ liệu trùng lặp (Double Scan), ta áp dụng kỹ thuật Single-Pass Validation Tagging:

# PySpark logic gắn thẻ lỗi
from pyspark.sql import functions as F

df_validated = df_flattened.withColumn(
    "validation_errors",
    F.concat_ws(";",
        F.when(F.col("id").isNull(), F.lit("ERR_NULL_ID")).otherwise(F.lit("")),
        F.when(F.col("amount") < 0, F.lit("ERR_NEGATIVE_AMOUNT")).otherwise(F.lit(""))
    )
)

# Tách luồng sạch và luồng lỗi
df_valid = df_validated.filter(F.col("validation_errors") == "")
df_dlq   = df_validated.filter(F.col("validation_errors") != "")

Plan xử lý DLQ: Lưu vào bảng Iceberg DLQ kèm error_code, raw_payload, ingested_at. Cài đặt Prefect Webhook cảnh báo nếu số lỗi vượt ngưỡng (ví dụ > 2%). Viết pipeline DLQ Replay chạy lại sau khi sửa logic hoặc nhận bản vá từ bên cung cấp API.

Vấn đề 3: Lưu Trữ Đa Mục Tiêu (MinIO + Trino Dev + Trino Prod)

Sử dụng df.cache() sau bước xử lý gốc để tránh tính toán lại khi ghi vào 3 đích:

  1. MinIO Backup (Bronze): Ghi append-only file thô theo phân vùng ngày /raw/{muc_name}/year=YYYY/month=MM/day=DD/.
  2. Trino Dev (Sandbox): Ghi đè hoặc append vào schema cá nhân để chạy notebook, thí nghiệm thuật toán.
  3. Trino Prod (Cleaned/Silver): Sử dụng MERGE INTO (nếu chạy qua Trino engine hoặc Spark Iceberg catalog) để upsert dữ liệu đã sạch, không tạo bản ghi trùng lặp.

Vấn đề 4: Xử Lý Incremental Multi-Version & Xung Đột Fact - Dimension

Hiện tượng: Bảng Dimension và Fact cùng được đẩy về trong 1 micro-window, dẫn đến Fact trỏ vào Dimension chưa kịp cập nhật (Late Arriving Dimension).

1. Điều phối Prefect

Thiết lập dependency bắt buộc: Luồng Dimension phải chạy xong Stage & Upsert SCD2 trước khi Fact Ingestion bắt đầu chạy Join.

2. Inferred Dimension Key

Nếu Fact xuất hiện ID lạ chưa có trong Dimension: Tự động chèn 1 bản ghi tạm (Dummy/Pending Member) với trạng thái status='INFERRED' để Fact không bị rớt.

3. Multi-version Window Deduplication trong Spark:

from pyspark.sql.window import Window

# Chỉ giữ lại bản ghi có phiên bản/updated_at mới nhất trong batch
window_spec = Window.partitionBy("business_id").orderBy(F.col("updated_at").desc(), F.col("version").desc())
df_deduped = df_valid.withColumn("rank", F.row_number().over(window_spec)).filter("rank = 1").drop("rank")

3. Checklist Chuẩn Bị Cho Buổi Làm Việc Ngày Mai

1. Về API Ingestion: Xác nhận chính xác Authentication (OAuth2 Bearer hay API Key?), Rate limit (bao nhiêu RPS, RPM?), và cơ chế phân trang (Cursor-based, Offset, hay Time-window?).
2. Về 4 Mục Dữ Liệu: Mục nào là Master/Dimension (khách hàng, danh mục) và mục nào là Transaction/Fact (giao dịch, sự kiện, log)?
3. Về Trino Catalogs: Trino đang dùng connector nào phía dưới (Apache Iceberg, Delta Lake, hay Hive Metastore)? Connector quyết định cú pháp MERGE INTO và tính năng Time Travel.
4. Về MinIO S3 Endpoint: Thông số kết nối S3A (Access Key, Secret Key, Endpoint URL, SSL enabled?) để Spark và Prefect đẩy backup an toàn.
